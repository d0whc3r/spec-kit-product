## Clarifications

### Session 2026-05-04

- Q: When `.specify/feature.json` is missing or points to a non-existent directory and multiple feature directories exist, how should the extension resolve the target feature directory? → A: Refuse and require the user to pass the feature directory explicitly (no auto-pick).
- Q: What is the scope of the mandatory product-spec template? → A: Lean core mandatory (summary, users/personas, JTBD, value prop, scope in/out, user-facing success metrics, risks, cross-link); positioning + GTM/rollout shipped as optional sections.
- Q: How should the extension behave when the source `spec.md` is incomplete (template placeholders vs unresolved `[NEEDS CLARIFICATION]` markers)? → A: Refuse on unfilled template placeholders; on `[NEEDS CLARIFICATION]` markers, warn + ask confirmation and surface them as open product questions per FR-018.
- Q: Final extension id and command name? → A: id `product`, command `speckit.product.spec` (slash form `/speckit-product-spec`); `product.<verb>` namespace reserved for future commands.
- Q: How is the extension distributed and installed by end users? → A: Packaged as a GitHub release zip (auto-generated by tag), installable via `specify extension add product --from <zip-url>` per Spec Kit's documented extension publishing flow; an automated release pipeline must build, validate, and publish the zip; a catalog.json entry is also produced for catalog-based discovery.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Generate a product specification from an existing technical spec (Priority: P1)

A product manager working alongside an engineering team that already uses Spec Kit wants to translate a finished `spec.md` (which today is feature/technical-leaning) into a complementary **product specification** that focuses on user value, market context, business outcomes, positioning, and go-to-market considerations — without re-typing the underlying feature description. They invoke a new Spec Kit slash command (e.g. `/speckit-product-spec`) inside the same feature directory and receive a generated `product-spec.md` artifact next to the existing `spec.md`.

**Why this priority**: Without this, product stakeholders either ignore Spec Kit (because its output is too engineering-shaped) or maintain a parallel doc by hand. Closing this gap is the core value of the extension; everything else is supporting.

**Independent Test**: Run `/speckit-product-spec` in a feature directory containing a populated `spec.md`. Confirm a `product-spec.md` is generated containing the mandatory product-spec sections, that it references the same feature, and that no engineering implementation details leak into the product artifact. Delivers value as a standalone slice even if no other extension command exists.

**Acceptance Scenarios**:

1. **Given** a feature directory `specs/NNN-feature/` containing a completed `spec.md`, **When** the user runs `/speckit-product-spec`, **Then** the extension creates `specs/NNN-feature/product/product-spec.md` populated from the source spec with all mandatory lean-core sections filled, and any unresolved `[NEEDS CLARIFICATION]` markers from the source spec are surfaced as open product questions in the output (per FR-018).
2. **Given** a `spec.md` that is empty or still contains unfilled template placeholders, **When** the user runs `/speckit-product-spec`, **Then** the command refuses to generate and reports the missing placeholders/sections (per FR-004).
3. **Given** a `product-spec.md` already exists for the feature, **When** the user re-runs `/speckit-product-spec`, **Then** the user is asked whether to overwrite or abort, and the existing file is not silently lost. (Merge/refresh is deferred to User Story 3.)
4. **Given** the feature directory is resolved through `.specify/feature.json`, **When** the command runs from any working directory inside the repo, **Then** the correct feature directory is targeted (no reliance on git branch name).

---

### User Story 2 - Install and discover the extension like any other Spec Kit extension (Priority: P2)

A team adopting Spec Kit wants to add the product-spec capability the same way they add other extensions: by following the documented Spec Kit extension layout so the `specify` CLI installs the files under `.specify/extensions/product/` and registers the extension in `.specify/extensions/.registry`, with the slash command then auto-discovered by their AI coding assistant. The extension ships as a self-contained directory with `extension.yml`, command files, and any helper scripts, mirroring the pattern of the existing `git` extension.

**Why this priority**: Adoption depends on Spec Kit users not having to reverse-engineer how to wire it in. If installation is bespoke, the extension dies on the shelf.

**Independent Test**: Starting from a Spec Kit project that does not have the extension, follow the documented install steps. Verify that the new slash command appears in the assistant's command list, that `.specify/extensions/.registry` lists the extension as installed, and that existing flows (including any hooks declared in `extensions.yml` for other extensions) continue to fire without interference.

**Acceptance Scenarios**:

1. **Given** a Spec Kit project with the extension files placed under `.specify/extensions/product/` and a corresponding entry in the CLI-managed `.specify/extensions/.registry`, **When** the user opens the project in their AI assistant, **Then** the new product-spec command is discoverable and invocable.
2. **Given** the extension is not present in `.specify/extensions/.registry`, **When** the user invokes the command, **Then** the system either does not surface it or fails gracefully with a clear "extension not installed" message; it does not corrupt the feature directory.
3. **Given** the existing `git` extension hooks (e.g. `before_specify`, `after_specify`), **When** the new extension is installed, **Then** those hooks continue to fire correctly and are not bypassed by the new command.

### User Story 4 - Publish the extension and install it from a Spec Kit project via the `specify` CLI (Priority: P2)

A maintainer of this extension wants to ship new versions to end users without asking them to clone the repo or copy files manually. End users want to type a single `specify extension add` command and have the product extension drop into their project, ready to run. The extension is therefore packaged as a GitHub release zip on every tagged release, with the version in `extension.yml` matched to the tag, and a catalog entry that points at the published zip URL.

**Why this priority**: distribution is the gate between "we built it" and "anyone can use it". Without a release pipeline, every install is a copy-paste exercise that the publishing guide explicitly tells extension authors to avoid. Promoted to P2 (above ongoing sync work) because it is what makes Stories 1 and 2 reachable for users outside this repo.

**Independent Test**: tag a commit `vX.Y.Z`, watch the release pipeline build the zip and create a GitHub Release. From an unrelated Spec Kit project, run `specify extension add product --from <zip-url>`. Confirm the extension lands under `.specify/extensions/product/`, the slash command is discoverable, and a smoke run of `/speckit-product-spec` succeeds.

**Acceptance Scenarios**:

1. **Given** a new commit tagged `vX.Y.Z` and pushed to the extension repository, **When** the release pipeline runs, **Then** a GitHub Release is created at that tag with an attached zip whose root contains `extension.yml`, `README.md`, `LICENSE`, and the `commands/` and `templates/` directories required by the extension.
2. **Given** the version field inside `extension.yml` does not match the git tag (without the `v` prefix), **When** the release pipeline runs, **Then** the pipeline fails with a clear "version mismatch" error and no release is published.
3. **Given** a published release zip URL, **When** an end user runs `specify extension add product --from <zip-url>` from a Spec Kit project, **Then** the extension is installed under `.specify/extensions/product/`, registered in the project's `.specify/extensions/.registry`, and `/speckit-product-spec` becomes available in the user's AI assistant.
4. **Given** the catalog.json file shipped alongside the release, **When** an end user runs `specify extension add product` (no `--from`) and the catalog is in scope, **Then** the CLI resolves the entry, downloads the same zip, and installs the extension identically to the explicit `--from` flow.

---

### User Story 3 - Keep product spec and technical spec in sync over time (Priority: P3)

As the technical `spec.md` evolves through `/speckit-clarify`, `/speckit-plan`, and edits, the product spec should not silently drift. A product owner can re-run the command (e.g. `/speckit-product --refresh`) and see what changed in the source spec, with proposed updates to `product-spec.md` they can accept or reject section-by-section.

**Why this priority**: Drift is a real failure mode for any "second artifact" generator, but a usable v1 can ship with overwrite/abort prompts (covered in Story 1) and add diff/merge later. P3, not P1.

**Independent Test**: Modify `spec.md` after generating `product-spec.md`. Re-run the command in refresh mode. Confirm the user is shown which sections of the product spec are now stale and is offered a per-section update.

**Acceptance Scenarios**:

1. **Given** a `product-spec.md` generated from an earlier version of `spec.md`, **When** the source spec changes and the user runs the refresh flow, **Then** the user sees a per-section diff of proposed updates and can accept or reject each.
2. **Given** the user rejects all proposed changes, **When** the refresh flow ends, **Then** `product-spec.md` is left untouched.

---

### Edge Cases

- The feature directory contains a `spec.md` whose `[NEEDS CLARIFICATION]` markers are still unresolved — the product spec must surface those gaps rather than silently fabricate answers.
- The feature directory exists but `spec.md` is missing entirely — command fails with a clear remediation message ("run `/speckit-specify` first").
- `.specify/feature.json` is missing or points to a directory that no longer exists — command refuses to run and instructs the user to re-run `/speckit-specify` or pass the feature directory explicitly (no auto-pick).
- The repo uses timestamp-based feature numbering (`YYYYMMDD-HHMMSS-...`) instead of sequential — the command must work identically.
- The user runs the command outside any Spec Kit project — command exits with a clear "no Spec Kit project detected" message.
- The source spec is in a non-English language — the command refuses to run and reports the detected language (per FR-013); v1 output is English-only and never auto-translates.
- Multiple feature directories exist and none is "current" — command requires the user to specify which one, rather than picking arbitrarily.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The extension MUST be packaged with the id `product` and MUST provide a Spec Kit command named `speckit.product.spec` (slash form `/speckit-product-spec`) that generates a product specification artifact for the current feature. The `product.<verb>` namespace is reserved for future product-shaped commands (e.g. a future refresh/merge command per User Story 3).
- **FR-002**: The extension MUST resolve the target feature directory using `.specify/feature.json` first. If that file is missing or points to a non-existent directory, the extension MUST refuse to run and instruct the user to either re-run `/speckit-specify` or pass the feature directory explicitly — it MUST NOT auto-select a directory under `specs/`.
- **FR-003**: The extension MUST read the existing `spec.md` in the target feature directory as its primary input and refuse to run if `spec.md` does not exist.
- **FR-004**: The extension MUST refuse to generate when `spec.md` still contains unfilled template placeholders (e.g. `[FEATURE NAME]`, `[Brief Title]`, raw template scaffolding from `spec-template.md`), and MUST report which placeholders/sections are missing. Unresolved `[NEEDS CLARIFICATION]` markers MUST NOT block generation; instead the extension MUST warn the user, list each marker, ask for confirmation to proceed, and (per FR-018) surface them as open product questions in the generated artifact.
- **FR-005**: The extension MUST write its output to `product/product-spec.md` inside the same feature directory, alongside (not replacing) `spec.md`. All generated artifacts live under a single `product/` subfolder so they are easy to identify, read, export, and share as a self contained bundle.
- **FR-006**: The extension MUST include a product-spec template with a **mandatory lean core**: product summary / one-liner, target users and personas, problem statement and jobs-to-be-done, value proposition and differentiation, scope (in/out), user-facing success metrics (north-star + supporting), risks and open product questions, and explicit cross-links back to the source `spec.md`. Positioning/messaging hooks and go-to-market/rollout MUST be present as **optional** sections in the template (clearly marked as optional), to be filled in only when relevant — teams without a GTM motion (e.g. internal tools) may omit them without failing the quality checklist.
- **FR-007**: The product spec MUST remain technology-agnostic: no frameworks, languages, APIs, data stores, or implementation patterns may appear in the generated artifact.
- **FR-008**: The extension MUST detect that an existing `product-spec.md` is present and prompt the user to choose between **overwrite** or **abort** — never overwrite silently. Merge/refresh is explicitly out of scope for v1 and arrives with User Story 3.
- **FR-009**: The extension MUST be packaged as a self-contained Spec Kit extension following the documented extension layout (an `extension.yml` manifest, command markdown files under a `commands/` subdirectory, optional helper scripts, optional config template) so that installing it places its files under `.specify/extensions/product/` and updates the project's CLI-managed registry at `.specify/extensions/.registry`. The project-level `.specify/extensions.yml` file remains the place where projects declare which installed extensions are active and how their hooks are wired (consistent with the bundled `git` extension); this extension does not register hooks (per FR-011) but its presence MAY be reflected in `extensions.yml` for tooling that reads it.
- **FR-010**: The extension's `extension.yml` MUST declare schema version, extension id, name, version, description, requires (Spec Kit version, tools), provides (commands), and tags, consistent with the existing `git` extension manifest.
- **FR-011**: The extension MUST NOT register hooks that fire automatically on Spec Kit lifecycle events (no `before_*` / `after_*` hooks in v1) — invocation is user-driven only, to avoid surprising overwrites.
- **FR-012**: The extension MUST honor the project's existing branch numbering mode (`sequential` vs `timestamp`) without modification, since it does not create branches itself.
- **FR-013**: The extension MUST produce its output in English. If `spec.md` is detected as non-English, the extension MUST refuse to run and report the detected language; auto-translation is forbidden. (English-only output is a v1 constraint chosen so generated artifacts share one canonical voice; future versions may relax this.)
- **FR-014**: The extension MUST emit a quality checklist file at `product/checklist.md` using the same checklist file format and checkbox conventions as the existing `requirements.md` checklist (markdown headings plus `- [ ]` items), so the product spec can be validated before downstream use. The internal grouping of checklist items is product-spec-specific and is defined canonically in `contracts/quality-checklist.md`.
- **FR-015**: The extension MUST work when invoked from any working directory inside the Spec Kit project, not only from the project root.
- **FR-016**: The extension MUST be cross-platform: it MUST ship parallel Bash and PowerShell helper scripts where helper scripts are needed, matching the convention used by the `git` extension.
- **FR-017**: The extension's documentation MUST include a README explaining install, invocation, and the source-of-truth contract ("`spec.md` is canonical; `product-spec.md` is derived").
- **FR-018**: When the source `spec.md` has unresolved clarifications, the generated `product-spec.md` MUST surface them as open product questions rather than guessing.
- **FR-019**: The extension MUST be packageable as a single zip whose **root** contains, at minimum: `extension.yml`, `README.md`, `LICENSE`, `CHANGELOG.md`, the `commands/` directory, and the `templates/` directory. The zip layout MUST follow the structure documented in Spec Kit's extension publishing guide so that `specify extension add ... --from <zip-url>` installs it without further manipulation. The zip MUST NOT contain unrelated repository content (specs, design docs, CI configuration); it MUST be built explicitly from the extension subtree, not from the GitHub-auto-generated tag archive.
- **FR-020**: A release pipeline MUST run automatically on push of a tag matching `v*.*.*`. The pipeline MUST: (a) verify the version field inside `extension.yml` equals the tag with the leading `v` removed, (b) verify required files exist at the root of the extension subtree (`extension.yml`, `README.md`, `LICENSE`, `commands/`, `templates/`), (c) lint the manifest against the documented Spec Kit schema, (d) build an explicit `product-<version>.zip` from the extension subtree (so the manifest lands at the zip root), (e) create a GitHub Release at the tag and attach that zip as a release asset.
- **FR-021**: The release pipeline MUST fail closed: any verification failure MUST abort the release before publication, and the failure reason MUST be reported clearly enough that the maintainer can fix and retag without guessing.
- **FR-022**: A `catalog.json` file MUST be maintained in the repository describing this extension as one entry, with the schema documented by Spec Kit (id, name, version, description, author, download_url, repository, license, requires.speckit_version, tags, created_at, updated_at). The pipeline MUST update at least the `version`, `download_url`, and `updated_at` fields on every release so that catalog-based installs (`specify extension add product` without `--from`) resolve to the latest published zip.
- **FR-023**: End users MUST be able to install the published extension into any Spec Kit project with a single command, either `specify extension add product --from <zip-url>` (direct URL) or `specify extension add product` (catalog-driven). The README MUST document both forms.
- **FR-024**: The repository MUST also support a developer install path (`specify extension add --dev <local-path>` or equivalent) so contributors can iterate on the extension without cutting a release. The README MUST document this path alongside the user-facing install instructions.

### Key Entities

- **Source Spec (`spec.md`)**: The technical/feature specification produced by `/speckit-specify`. Treated as canonical input. Read-only from this extension's point of view.
- **Product Spec (`product/product-spec.md`)**: The generated derived artifact. Written into a `product/` subfolder of the feature directory so all stakeholder facing output is identifiable and self contained. Carries product-shaped sections (personas, value prop, success metrics; positioning and GTM optional) and explicit links back to the source spec.
- **Product Spec Template**: A markdown template shipped with the extension that defines the mandatory sections and section ordering for every generated `product-spec.md`.
- **Product Quality Checklist**: A checklist file (`product/checklist.md`) used to validate completeness of the generated artifact, mirroring the role of `checklists/requirements.md` for the technical spec but kept inside the `product/` bundle so it ships alongside the product spec.
- **Extension Manifest (`extension.yml`)**: Declares the extension identity, version, provided commands, requirements, and (intentionally empty) hooks.
- **Release Zip**: The deliverable artifact produced on every tagged release. Built by the release pipeline from the `extension/` subtree (so `extension.yml` lands at the zip root), attached to the GitHub Release as a release asset, and downloadable at `https://github.com/<owner>/<repo>/releases/download/v<version>/product-<version>.zip`. Consumed by `specify extension add ... --from <url>`. The pipeline does not rely on GitHub's auto-generated tag archive, since that archive zips the entire repo and would not place the manifest at the zip root.
- **Catalog Entry (`catalog.json`)**: A JSON record describing the extension, its current `version`, and the `download_url` of the latest release zip. Allows `specify extension add product` (no `--from`) to resolve and install.
- **Release Pipeline**: The automated workflow that runs on tag push. Validates the manifest, asserts the tag-version match, lints, and publishes the GitHub Release. Documented in the repository as a CI configuration file.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: A user with a populated `spec.md` can produce a complete `product-spec.md` for that feature in under 2 minutes from typing the command to having a reviewable artifact.
- **SC-002**: 100% of generated `product-spec.md` files pass the shipped product quality checklist on first generation when the source spec is itself complete (no missing sections, no template placeholders).
- **SC-003**: 0% of generated product specs contain implementation details (frameworks, languages, APIs, data stores), as measured by a reviewer audit on a sample of 10 generated specs.
- **SC-004**: Installation by a Spec Kit user (via `specify extension add product --from <zip-url>`, or the catalog-driven equivalent, or the `--dev` developer path) takes under 5 minutes and requires no edits to core Spec Kit files.
- **SC-005**: When `spec.md` has unresolved `[NEEDS CLARIFICATION]` markers, 100% of well-formed markers are reflected as open product questions in the generated artifact, measured on a sample of test specs. Malformed markers (e.g. unbalanced brackets, missing colon, no body) are reported separately as parse warnings rather than counted as silent drops.
- **SC-006**: Re-running the command on a feature that already has a `product-spec.md` never silently destroys prior content. Verified manually by the release smoke test: with an existing `product-spec.md` in place, the user is always shown the overwrite-or-abort prompt before any write occurs, and choosing abort leaves the file byte-identical.
- **SC-007**: The extension does not break any existing Spec Kit lifecycle command (`/speckit-specify`, `/speckit-clarify`, `/speckit-plan`, `/speckit-tasks`, `/speckit-implement`); full lifecycle smoke test passes after install.
- **SC-008**: From a clean Spec Kit project, an end user can install the published extension and run `/speckit-product-spec` for the first time in under 3 minutes wall-clock, using only the documented `specify extension add` command.
- **SC-009**: 0% of attempted releases bypass the pipeline's manifest validation. Every published zip has the manifest version equal to the git tag (without the `v` prefix) and contains every required file from `contracts/package-layout.md`. Failure-mode rate is measured automatically by the pipeline's own pass/fail history over a rolling 6-month window.
- **SC-010**: The catalog entry's `version` and `download_url` fields point at the latest published release within 5 minutes of a successful release, measured by the pipeline's own logs.

## Assumptions

- The target users are Spec Kit users (PMs, product owners, designers, founders) operating in projects that already use the `/speckit-*` workflow; the extension does not need to onboard users to Spec Kit itself.
- `spec.md` produced by `/speckit-specify` is the single canonical input; the extension does not pull from issue trackers, design tools, or external systems in v1.
- The extension runs inside an AI coding assistant compatible with Spec Kit slash commands (Claude Code, Copilot, etc.); the AI does the language-model-driven content transformation, the extension provides the prompt scaffolding, template, and file plumbing.
- The product-spec template is opinionated but generic enough to serve B2B SaaS, B2C, internal-tools, and dev-tools contexts without specialization in v1.
- Refresh / diff-merge behavior (User Story 3) is desirable but explicitly deferred from the MVP; v1 ships with overwrite/abort prompting only.
- The extension follows the same on-disk layout as the existing `git` extension at `.specify/extensions/git/` (manifest + `commands/` + `scripts/{bash,powershell}/` + README + config template), since that pattern is already validated in this project.
- Spec Kit's documented extension layout (per `https://github.github.io/spec-kit/reference/extensions.html`) is stable enough across recent versions that an extension authored against the current `git` extension shape will load correctly; if Spec Kit changes its extension contract, this extension will need a manifest update but not a redesign.
- No new runtime dependencies (package managers, runtimes, services) are introduced; the extension is plain markdown command files plus optional shell/PowerShell scripts, like the existing `git` extension.
- The extension is hosted in a GitHub repository whose `extension/` subtree contains the canonical extension source. Non-extension files (this spec, internal scripts, dev tooling, CI configuration) live outside that subtree and are excluded from packaging. The release pipeline builds an explicit `product-<version>.zip` from `extension/` and attaches it as a release asset; it does not rely on GitHub's auto-generated tag archive (which would include the whole repo).
- The release pipeline runs on GitHub Actions, since the project already lives on GitHub and this incurs no additional infrastructure cost. Other CI providers could be substituted later without changing the contract.
- The Spec Kit `specify extension add` CLI and the catalog schema are stable enough at the time of release that an extension authored against the documented publishing guide installs without further glue.
