# Data Model: Product Spec Extension

**Feature**: 001-product-spec-extension
**Date**: 2026-05-04
**Note**: This extension stores no databases and no application state. The "data model" here describes the small set of files and configuration objects the extension reads and writes, plus their relationships.

## Entities

### Source Spec

**Represents**: the canonical technical specification for a feature, produced by `/speckit-specify`.

**Location**: `specs/<feature-dir>/spec.md`.

**Role for this extension**: read only input.

**Fields consumed**:

- Feature name (heading line one).
- User stories and their priorities (P1, P2, P3).
- Acceptance scenarios.
- Functional requirements.
- Success criteria.
- Edge cases.
- Assumptions.
- Any unresolved `[NEEDS CLARIFICATION]` markers.

### Product Spec

**Represents**: the derived product oriented specification, generated by this extension.

**Location**: `specs/<feature-dir>/product/product-spec.md`, inside a `product/` subfolder of the feature directory so all stakeholder facing output is bundled together for easy export and sharing.

**Lifecycle**:

1. Created on first run of `/speckit-product-spec`.
2. On subsequent runs, the user is prompted to overwrite or abort. Merge or refresh is out of scope for v1 and arrives with User Story 3.

**Sections** (defined canonically in `contracts/product-spec-template.md`): headline summary, target users and personas, problem statement (Jobs to Be Done), value proposition, scope, out of scope, use cases (Gherkin scenarios), success metrics, risks and open product questions, optional positioning, optional go to market, source spec link.

### Product Quality Checklist

**Represents**: the per feature checklist used to validate the generated product spec.

**Location**: `specs/<feature-dir>/product/checklist.md`, inside the same `product/` bundle as the generated product spec.

**Lifecycle**: written once when the product spec is first generated. Re-written when the product spec is regenerated (overwrite path).

**Fields**: a list of pass or fail items, one per mandatory section of the product spec, plus content quality items (English only, no em dash, no implementation details, etc.). Defined canonically in `contracts/quality-checklist.md`.

### Feature Pointer

**Represents**: the pointer that tells the extension which feature directory to operate on.

**Location**: `.specify/feature.json`, key `feature_directory`.

**Role**: primary input for resolving `<feature-dir>`. If missing or pointing to a non existent directory, the extension refuses to run (per FR-002).

### Extension Manifest

**Represents**: the registration record for the extension itself.

**Location**: `.specify/extensions/product/extension.yml`.

**Fields**: `schema_version`, `extension.id` (`product`), `extension.name`, `extension.version`, `extension.description`, `extension.author`, `requires.speckit_version`, `provides.commands`, `tags`. Hooks block is intentionally empty in v1 (per FR-011).

### Extensions Registry

**Represents**: the project's record of which extensions are installed and active.

**Location**: `.specify/extensions.yml`, key `installed`.

**Fields read or written by this extension**: the entry for `product` is added to the `installed` list during install. The extension itself does not modify this file at runtime.

### Product Spec Template

**Represents**: the master template for generated product specs.

**Location at runtime**: `.specify/extensions/product/templates/product-spec-template.md`.

**Canonical source of truth**: `specs/001-product-spec-extension/contracts/product-spec-template.md`. The runtime copy is deployed from the canonical source during install.

### Product Checklist Template

**Represents**: the master template for the per feature quality checklist.

**Location at runtime**: `.specify/extensions/product/templates/product-checklist-template.md`.

**Canonical source of truth**: `specs/001-product-spec-extension/contracts/quality-checklist.md`.

### Release Zip

**Represents**: the deliverable artifact consumed by `specify extension add ... --from <zip-url>`.

**Filename**: `product-<version>.zip`.

**Location**: attached as a release asset to the GitHub Release at tag `v<version>`. Download URL: `https://github.com/<owner>/<repo>/releases/download/v<version>/product-<version>.zip`. The pipeline does not use GitHub's auto-generated tag archive (which would zip the entire repo, not the extension subtree).

**Built from**: the `extension/` subtree of the repository.

**Contents and validation**: pinned in `contracts/package-layout.md`. Files at the zip root only (no nested wrapper directory).

**Lifecycle**: immutable once published. Re-tagging an already-released version is rejected by the pipeline.

### Catalog Entry

**Represents**: the metadata record that makes catalog-driven installs (`specify extension add product` without `--from`) resolve to the latest published zip.

**Location**: `catalog.json` at the repository root.

**Schema and update rules**: pinned in `contracts/catalog-entry.md`. The pipeline owns the `version`, `download_url`, `requires.speckit_version`, `updated_at`, and (on first release) `created_at` fields.

### Release Pipeline

**Represents**: the automated workflow that validates, builds, publishes, and updates the catalog on every tag push.

**Location**: `.github/workflows/release.yml`.

**Trigger**: tag push matching `v*.*.*`. Pull requests trigger validation-only runs.

**Gates and outputs**: pinned in `contracts/release-pipeline.md`. Fail-closed.

## Relationships

```text
Feature Pointer ──────► Source Spec
                            │
                            │ (input to generation)
                            ▼
                       Product Spec  ◄────  Product Spec Template
                            │
                            │ (validates against)
                            ▼
                  Product Quality Checklist  ◄────  Product Checklist Template

Extensions Registry ──────► Extension Manifest ──────► Slash Command (speckit.product.spec)

Tag push (v*.*.*) ──► Release Pipeline ──► Release Zip ──► Catalog Entry
                            │
                            │ (gate: tag-version match, package layout, content lint)
                            ▼
                          (fail-closed: no zip, no release, no catalog update)
```

## Validation Rules

- **VR-1**: A Product Spec MUST exist in the same feature directory as its Source Spec. The two files are paired by directory, never by name lookup.
- **VR-2**: A Product Spec MUST contain every mandatory section listed in the Product Spec Template. Optional sections may be present or absent.
- **VR-3**: A Product Spec MUST be written in the same natural language as its Source Spec. Auto translation is forbidden.
- **VR-4**: A Product Spec MUST NOT contain implementation details (frameworks, languages, APIs, data stores, code, file paths beyond the cross link to `spec.md`).
- **VR-5**: A Product Spec MUST NOT contain em dashes.
- **VR-6**: Each Use Case scenario in a Product Spec MUST contain exactly one Given line, one When line, and one Then line, each a full sentence starting with the keyword.
- **VR-7**: Each generated Product Spec MUST include a link back to its Source Spec, expressed as a relative path to `spec.md` in the same directory.
- **VR-8**: The Product Quality Checklist MUST list one validation item per mandatory section of the Product Spec, plus the content quality items defined in the canonical checklist contract.

## Out of Model

This extension does not model: users, sessions, permissions, network state, telemetry, billing, internationalization beyond same language passthrough. Those concerns are absent because the extension runs locally as a slash command in the user's existing AI assistant.
