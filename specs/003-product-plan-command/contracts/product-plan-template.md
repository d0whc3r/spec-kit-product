# Template Contract: product-plan-template.md

This contract defines the structure and rules for the `product-plan-template.md` template. It is the authoritative reference for both the template author and the command body. Any change to a section name, order, or mandatory/optional status is a breaking change and requires a version bump.

## Purpose

`product-plan-template.md` is the structural skeleton for `product/plan.md`, the high-level product-oriented implementation plan generated by `/speckit.product.plan`. The template uses four structured techniques:

- **Shape Up appetite framing** - each delivery phase carries a rough time-box that bounds the work without committing to calendar dates.
- **C4 container-level descriptions** (optional) - main system parts affected, named and described in one sentence each, at the container level only.
- **Condensed ADR summaries** (optional) - key design decisions distilled to: what was chosen, why, and what was accepted as a trade-off.
- **NOW/NEXT/LATER delivery view** - the Delivery Phases section structured as three horizon bands.

## Section inventory

| # | Section name | Type | Always present |
|---|---|---|---|
| - | Header metadata | Metadata | Yes |
| 1 | Summary | Prose | Yes |
| 2 | Delivery Phases | Structured (NOW/NEXT/LATER) | Yes |

## Template source

```markdown
# Product Plan: [FEATURE NAME]

**Feature**: [###-feature-name]
**Source Plan**: [plan.md](../plan.md)
**Created**: [DATE]
**Status**: Draft

## 1. Summary

> One paragraph, three to five sentences. What is being built, why it is being built now, and what the main approach is. No code. No file paths. Technical terms glossed on first use.

[Paragraph here.]

## 2. Delivery Phases

> Structure this section as three bands. NOW describes the phases of the current feature. NEXT is the natural follow-on after this feature ships (not committed). LATER is explicitly deferred work.

### NOW

> Each phase: name, appetite (rough time-box in plain units), and two to four outcome bullets. Outcomes are things delivered, not tasks performed.

#### Phase 1: [Phase Name]

**Appetite**: [e.g., one to two weeks]

- [Outcome delivered by this phase, one sentence ending with a period.]
- [Outcome delivered by this phase, one sentence ending with a period.]
- [Outcome delivered by this phase, one sentence ending with a period.]

#### Phase 2: [Phase Name]

**Appetite**: [e.g., two to three days]

- [Outcome delivered by this phase, one sentence ending with a period.]
- [Outcome delivered by this phase, one sentence ending with a period.]

### NEXT

> The natural next capability or feature after this one ships. One to three short bullets. Not a commitment.

- [What comes next, one sentence.]

### LATER

> Explicitly deferred work. Drawn from the Out of Scope list. One to three short bullets.

- [What is deferred and a brief reason, one sentence.]

## 3. Out of Scope

> A short, scannable list of what is explicitly not included, even though a reasonable reader might expect it. Always populate this section. Each item is one short sentence with a one-phrase reason.

- [Capability deliberately excluded, with one short reason.]
- [Capability deliberately excluded, with one short reason.]

## 4. Component Overview *(optional)*

> Include this section only when the source plan contains architecture or component information. Omit the entire section otherwise - do not write "none" or "N/A".
>
> List the main system parts that this feature adds, changes, or depends on. Each part is one bullet: name, one-sentence responsibility, and whether this feature adds or modifies it. C4 container level only - no classes, no functions, no internal wiring.

- **[Component name]**: [What it does, one sentence. This feature [adds / modifies] it.]
- **[Component name]**: [What it does, one sentence. This feature [reads from / depends on] it.]

## 5. Key Technical Decisions *(optional)*

> Include this section only when the source plan contains explicit design decisions. Omit the entire section otherwise.
>
> Each decision uses the condensed ADR (Architecture Decision Record) format: Decision, Why, Trade-off.

### [Decision title]

**Decision**: [What was chosen, one sentence.]
**Why**: [The plain-language reason, one to two sentences.]
**Trade-off**: [What was accepted or given up, one sentence.]

---

### [Decision title]

**Decision**: [What was chosen, one sentence.]
**Why**: [The plain-language reason, one to two sentences.]
**Trade-off**: [What was accepted or given up, one sentence.]

## 6. Risks *(optional)*

> Include this section only when the source plan contains concrete risk signals. Apply the pre-mortem lens: imagine this feature shipped and quietly failed - what caused it? Two to four bullets. Each bullet names one risk and its consequence in one sentence. Omit generic or speculative risks. Remove the entire section when the source plan has no meaningful risk signals.

- [Risk and its consequence, one sentence.]
- [Risk and its consequence, one sentence.]

## 7. Open Questions *(optional)*

> Include this section only when the source plan contains open questions or marked assumptions AND the user confirmed at the prompt. Each item becomes one bullet as a single-sentence question. Never silently resolve an open question.

- [Open question in one sentence.]
- [Open question in one sentence.]
```

## Rules for the command body

1. Read this template verbatim. Do not modify section names, order, or the mandatory/optional classification.
2. Replace every bracketed placeholder with concrete content drawn from `plan.md` (and `spec.md` when available).
3. Omit optional sections entirely (including the heading) when the source has no content for them.
4. Apply all writing rules defined in the command contract: no em dash, plain English, active voice, no AI-tell phrases, no code, no file paths, glossed technical terms on first use.
5. Do not invent phases, decisions, or components not present in the source `plan.md`.
6. The `> blockquote` lines in the template are guidance notes for the AI. They must not appear in the generated output.
