# Implementation Plan: Product Plan Command

**Branch**: `003-product-plan-command` | **Date**: 2026-05-04 | **Spec**: [spec.md](spec.md)
**Input**: Feature specification from `specs/003-product-plan-command/spec.md`

## Summary

The `product` extension currently generates two stakeholder documents from a feature's `spec.md`: a full PRFAQ-style spec (`product/spec.md`) and a one-page summary (`product/info.md`). Neither covers the implementation plan. This feature adds a third sibling command, `/speckit.product.plan`, that reads the engineering `plan.md` and produces `product/plan.md` - a high-level, product-oriented plan that answers "how are we building this?" for product managers and cross-functional leads.

The artifact uses four structured techniques: Shape Up appetite framing for phases, C4-inspired component descriptions at the container level, condensed ADR (Architecture Decision Record) summaries for key design decisions, and a NOW/NEXT/LATER delivery view. Technical terms are used but always glossed in plain English on first use. No code, no file paths, no task-level detail.

The implementation is purely additive. One new command file, one new template, an updated manifest, and updated lint rules. The existing cross-platform resolver scripts are reused without change.

## Methodology notes (from Phase 0 research)

See `research.md` for full rationale. The four techniques used in the generated artifact are:

- **Shape Up appetite**: Each phase carries a rough time-box (e.g., "one to two weeks"). It is not an estimate; it bounds the work and communicates relative weight without committing to dates. Drawn from the engineering plan's phase scope.
- **C4 container level**: The Component Overview section lists the main runtime parts affected: name, one-sentence responsibility, whether this feature adds or modifies it. Context and container levels only - no internal class or function detail.
- **Condensed ADR**: Each key decision is three lines - Decision (what was chosen), Why (plain-language reason), Trade-off (what was accepted). No full ADR boilerplate.
- **NOW/NEXT/LATER**: Delivery Phases structured as three bands. NOW = current feature phases. NEXT = natural follow-on (not committed). LATER = explicitly deferred work from Out of Scope.

## Writing rules for the generated product/plan.md

These rules govern all prose generated by the command. They extend the rules already enforced by sibling commands.

1. **English only.** All output in English. If `plan.md` is not in English, refuse with `E_LANGUAGE`.
2. **No em dash.** The character `—` must not appear. Use commas, parentheses, colons, semicolons, or sentence breaks. Hyphens are allowed.
3. **Plain English.** Active voice, short sentences, human tone.
4. **No AI-tell phrases.** Banned: "delve", "tapestry", "in essence", "navigate the landscape", "leverage" (standalone verb without a concrete object), "robust" (without a measurable target), "seamless", "intuitive". This list is inherited verbatim from the sibling commands.
5. **No implementation detail.** No code, no framework names, no library names, no file paths. The only allowed file path is `[plan.md](../plan.md)` in the metadata block.
6. **Technical terms glossed on first use.** The following terms must carry a plain-language gloss in parentheses on the same line as their first occurrence: "API", "CLI", "SDK", "refactor", "idempotent", "atomic", "schema", "linter", "manifest", "hook", "pipeline". Subsequent occurrences of the same term require no gloss.
7. **Bullets are short. Prose is full sentences.**
8. **No invented content.** The command must not invent phases, decisions, or components not present in the source `plan.md`.

## Key Technical Decisions

### Decision 1: Input sources

**Decision**: Read `plan.md` as the primary source. Read `spec.md` when present as supplementary context for the Summary Why Now framing and persona information.
**Why**: The engineering plan contains the implementation information that the product plan summarises. The feature spec adds the user-facing framing that engineering plans often omit. Reading both when available produces a richer, more coherent Summary section without requiring the user to do anything extra.
**Trade-off**: The command must produce useful mandatory sections from `plan.md` alone, without depending on `spec.md`. If `spec.md` is absent, the Summary may be less rich but must still be complete.

### Decision 2: Mandatory vs optional sections

**Decision**: Classify template sections as mandatory (Summary, Delivery Phases, Out of Scope - always present) or optional (Component Overview, Key Technical Decisions, Risks, Open Questions - omitted entirely when the source has no relevant content).
**Why**: A section with a "none identified" placeholder is worse than no section at all for a communication artifact. Readers see a clean, complete document rather than one with obvious gaps.
**Trade-off**: The command must inspect the source `plan.md` to determine which optional sections have content before deciding what to include. This adds a content-inspection step before generation.

### Decision 3: Placeholder detection list

**Decision**: Use the explicit list of placeholder strings derived from the actual Spec Kit plan template at `.specify/templates/plan-template.md`: `[FEATURE]`, `[DATE]`, `[###-feature-name]`, `[link]`, `[Extract from feature spec: primary requirement + technical approach from research]`.
**Why**: An explicit list is accurate, predictable, and easy to test. It is consistent with the detection approach already used by `/speckit.product.spec` and `/speckit.product.info`. A heuristic pattern (e.g., matching any `[BRACKETED]` token) risks false positives on legitimate plan content.
**Trade-off**: The list is tied to the current plan template version. If the plan template changes its placeholder strings, this list must be updated alongside it.

### Decision 4: Sparse plan handling

**Decision**: Proceed with generation when `plan.md` is valid but sparse (no phases, decisions, or components). Emit a non-blocking console notice rather than refusing.
**Why**: A sparse plan produces a short but valid product plan (mandatory sections only). Refusing would block users whose features are genuinely small. The notice preserves transparency without over-engineering the check.
**Trade-off**: The generated artifact may not be useful for the audience if the source plan has very little content. The notice is the only mitigation; the user must decide whether to proceed.

## Risk Register

**Risk 1: Sparse plan produces a thin artifact.**
If the engineering plan for a feature is minimal, the product plan will contain only the mandatory sections, which may not be informative enough for the intended audience. The console notice mitigates this by making the limitation visible at generation time.

**Risk 2: Jargon-gloss rule is inconsistently applied by the AI.**
The host AI assistant may apply the first-use gloss rule inconsistently, especially for long documents. The linter provides a post-generation catch, but linting operates on the output rather than guiding the generation. The command body includes explicit instructions with the full banned-jargon list to reduce this risk.

**Risk 3: Template and command body drift.**
If `templates/product-plan-template.md` is modified independently of the command body, section names or order may fall out of sync. The fixed-section-order rule and the lint check for unexpected sections are the mitigations.
